# Languages and translation

Seven languages ship: English (default), Thai, Korean, Japanese, Vietnamese,
Indonesian and Simplified Chinese. Which are switched on is the `languages`
setting; the default is `default_lang`.

## URLs

The **default language has no prefix**; every other language has one.

```
/s/handbook/writing        English (the default)
/th/s/handbook/writing     Thai
/ja/s/handbook/writing     Japanese
```

That choice keeps every URL that existed before this feature working unchanged,
and means a site that never enables a second language never grows a locale
segment at all.

The **path is shared across languages** — the slug is not translated. Swapping
one segment moves a reader between languages without losing their place, links
translate mechanically, and the redirects table does not have to be maintained
per language.

**The URL is the single authority** for both the content and the interface. A
page showing English text under a Thai interface is confusing, and worse, it
makes the language of a shared link depend on who opens it. The reader's own
preference is honoured at `/` only, and remembered in a cookie thereafter.

## Two different `lang` questions

These are not the same and must not share a parameter name:

| | Means | Set by |
| --- | --- | --- |
| URL prefix | the language being **read** | `/th/...`, or `?setlang=th` to switch and remember |
| `?lang=` | the language being **edited** | the editor's language picker |

A translator writes Thai while reading English, so the two genuinely differ.
They were briefly spelled the same during development and every editor request
bounced through a 302 instead of doing its job.

## Content model

`pages` holds the tree and is language-neutral. `page_locales` holds one row per
page per language that exists, pointing at that language's current revision.
`page_revisions` carries a `lang`, so **each language has its own independent
history** — editing the Thai page does not create a revision of the English one,
and reverting one never touches another.

A language with no row simply does not exist for that page.

## What a reader is told

Three separate conditions, each stated plainly, because they mean different
things:

- **Fallback** — no translation exists, so the default language is shown. Better
  than a 404 for a page that plainly exists.
- **Machine translated** — written by `Core\Translator`, not a person.
- **Out of date** — the source language has changed since this translation was
  made from it.

Staleness works because `page_locales.translated_from_revision_id` records
*which* source revision a translation came from; comparing revision ids (which
are monotonic) rather than timestamps means two saves in the same second are
still distinguishable.

A human editing a translation directly passes `0` for that field, so it is not
advanced — they have not necessarily read the source, and claiming otherwise
would make the staleness banner lie in the reader's favour.

## Search

**Two FULLTEXT tables, because MySQL allows one parser per index.**

| Table | Parser | Languages |
| --- | --- | --- |
| `page_search` | default (splits on whitespace) | en, ko, vi, id |
| `page_search_cjk` | `ngram`, size 2 | th, ja, zh |

Thai, Japanese and Chinese do not put spaces between words. Under the default
parser an entire Thai sentence is a single token, so the only query that could
ever match it is that exact sentence — search silently returns nothing. This is
not tuning; it is the difference between working and not.

Verified against real data: the Thai term `ติดตั้ง*` scores 0 hits in
`page_search` and 1 in `page_search_cjk`.

The language list appears in three places — `sp_revision_create`, `sp_search`
and `Core\I18n::usesNgram()`. **They must agree**; a mismatch indexes content in
one table and searches the other, which fails by simply never matching.

`SearchController` also lowers the minimum term length from 3 to 2 for ngram
languages, since the parser tokenises in pairs.

## Machine translation

Off unless configured. Set `mt_driver` in settings and `MT_KEY` in `.env` —
the key stays out of the settings table, which is editable from a web form and
readable by every admin.

- **google** — Google Cloud Translation API v2. Needs an API key and a billing
  account, charged per character. This is the paid Cloud API; the free
  "Website Translator" page widget was discontinued and has no free
  replacement.
- **libretranslate** — self-hosted. No per-character cost and nothing leaves
  your network, at the price of running it and noticeably weaker output for the
  Asian languages here.

Translation is **always explicit** — an editor presses a button for one page and
one language. Nothing is translated on save. Cost is per character, and content
leaving your server should be a decision someone makes rather than discovers.

Output is stored as a **draft** marked `machine` and shown with a badge. It is a
starting point for a person, not something to put in front of readers unread.

Non-public spaces are refused unless `mt_allow_private` is set to `1`: sending an
internal space's text to a third party is the disclosure the space existed to
prevent.

Before translating, code blocks, inline code, URLs and container fences are
replaced with opaque `⟦n⟧` tokens and restored afterwards — a translator will
otherwise happily localise a file path or an identifier. Link *text* is left
translatable; only the URL is masked. A token the engine mangles is left visible
on purpose, so a reviewer can see exactly where to look rather than having a
code block silently deleted.

## UI strings

`app/Lang/{code}.php`, plain arrays. `app/Lang/en.php` is the canonical key set;
a key missing from a translation falls back to English, so a half-translated
catalogue shows English in the gaps rather than blanks.

Add a string to `en.php` first. `:name` placeholders must stay identical across
languages — a translation that renames or drops one prints the literal token.

The switcher lists **endonyms** (日本語, ไทย), not English names: a reader who
needs the Japanese option cannot necessarily read the word "Japanese".

> **The translations in `app/Lang/` were produced without a native speaker's
> review.** They are careful and use standard software terminology, but a native
> reviewer should go over them before this is put in front of real users of
> those languages. The keys and the machinery are correct regardless.

## Typography

Thai stacks tone marks above and vowels below the baseline; at Latin's 1.6
line-height they collide with the line above. Thai gets 1.85, CJK 1.8. Font
stacks list Latin faces first and CJK/Thai after, so a mixed sentence uses the
right face for each run.

## Adding a language

1. Add it to `I18n::LANGUAGES` with its endonym and whether it needs ngram.
2. If ngram, add the code to the lists in `sp_revision_create` and `sp_search`.
3. Copy `app/Lang/en.php` to `app/Lang/<code>.php` and translate.
4. Add the code to the `languages` setting.
5. Check the font stack covers its script.
